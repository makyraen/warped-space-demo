# measurements — 논문 §IV 수치 측정 하네스

`PAPER_DRAFT.md` §IV에 들어가는 수치를 **재현 가능하게** 뽑기 위한 스크립트다.
손으로 코드를 고쳐가며 값을 얻지 않고, 앱을 그대로 띄운 채 계측한다.

## 준비

```bash
cd measurements && npm install     # playwright
npx playwright install chromium    # 최초 1회
```

앱을 띄워 둔다(저장소 루트에서):

```bash
python -m http.server 8777
```

## 실행

```bash
node measurements/energy_drift.mjs      # §4.1 적분기 정확도
node measurements/precession.mjs        # §4.2 근일점 세차
```

원자료는 `measurements/results/*.json`에 저장된다.

## 설계 원칙

- **`?debug` 훅**: `main.js` 끝에서 `?debug` 쿼리가 있을 때만 `window.__warped`를 연다.
  일반 실행이나 배포본에는 노출되지 않는다. 스크립트는 이 훅으로 앱의 실제 함수를 직접 구동한다.
- **통제**: 적분기를 비교할 때 힘 계산은 앱의 `computeAcceleration()`을 **그대로** 쓰고
  스텝을 밟는 방식만 바꾼다. 비교 대상이 적분 스킴이므로 이것이 올바른 통제다.
- **동기 실행**: 측정 루프는 하나의 `page.evaluate()` 안에서 동기로 돌아 rAF 루프가 끼어들지 않는다.
- **⚠️ 초기조건 고정 필수**: `initGeodesic()`이 이심률에 `Math.random()`을 쓴다.
  측정에서는 `geo = {r, phi, vr, L}`(또는 위치·속도)를 **반드시 명시적으로 덮어쓸 것.**
  이걸 놓치면 실행마다 다른 궤도가 되어 비교가 성립하지 않는다(실제로 한 번 겪었다).

## 기록된 결과

### §4.1 적분기 정확도 (`energy_drift.mjs`)

2체계(중심 고정 `m₀=200`, 위성 `m₁=20`), `r₀=250`, 접선속도 40(원궤도 속도 약 85보다 낮음),
`Δt=1/120`, 24,000스텝(약 20공전).

| 적분기 | Δt | 최대 `|ΔE/E₀|` | 세속 표류 | `r` 범위 |
|---|---|---|---|---|
| semi-implicit Euler | 고정 | 5.40e-1 % | 5.02e-7 | 62.2–250.0 |
| leapfrog | 고정 | 3.62e-3 % | 3.22e-10 | 62.2–250.0 |
| semi-implicit Euler | ±50% 지터 | 8.17e-1 % | 1.84e-6 | 62.2–250.1 |
| leapfrog | ±50% 지터 | 5.81e-3 % | −6.61e-8 | 62.2–250.0 |

**결론**: leapfrog가 최대 오차 약 149배, 세속 표류 약 1,550배 개선.
**단, 둘 다 발산하지 않는다** — 원본의 Euler는 explicit이 아니라 semi-implicit(심플렉틱)이므로
고정 Δt에서 에너지가 유계 진동하는 것이 정상이다.
따라서 **"Euler라서 궤도가 붕괴한다"는 서술은 쓰면 안 된다.** 근거는 정확도 향상이다.

### §4.2 근일점 세차 (`precession.mjs`)

측지선 방정식에서 **`−3ML²/r⁴` 항만 켜고 끄며** 동일 `M`·`L`·`r_peri`로 적분.
(앱의 RUBBER 모드와 비교하면 안 된다 — 단위계가 달라 사과-오렌지가 된다.)

**검증 0**: 하네스 가속도 함수가 앱의 `geodesicRadialAccel()`과 상대차 **0**으로 일치.

| 검증 | 결과 |
|---|---|
| 보정항 제거 시 | 세차 −0.00001° ≈ 0 → **세차의 유일한 원인이 그 항** |
| 시간간격 1/8 | 세차각 동일(87.5677° → 87.5679°, 0.000%) → **수렴 확인** |
| 주기 간 편차 | 1e-12 ~ 1e-9 rad |

**약장 극한 수렴** (`r_peri`=150, `kL`=1.15):

| M | 2M/p | 측정 | 이론 6πM/p | 상대오차 | 오차÷(M/p) |
|---|---|---|---|---|---|
| 1 | 0.01004 | 5.5462° | 5.4199° | 2.331 % | 4.645 |
| 0.5 | 0.00503 | 2.7474° | 2.7161° | 1.153 % | 4.584 |
| 0.25 | 0.00252 | 1.3674° | 1.3596° | 0.573 % | 4.554 |
| 0.125 | 0.00126 | 0.6821° | 0.6802° | 0.286 % | 4.537 |

M을 절반으로 줄일 때마다 오차도 절반 → **잔차가 M/p에 1차 비례**하고 정규화 잔차가 ~4.54로 수렴.
이론값이 최저차 항이므로 이는 **고차항(물리)이지 구현 오류가 아니다.**

**데모 조건**(M=10, `r_peri`=150): 주기당 **87.57°**. 같은 `L`·`r_peri`인데도 보정항 유무에 따라
원일점이 196.2 대 332.4로 갈린다 — 이 영역에서 보정항은 궤도의 **방향뿐 아니라 형상**을 바꾼다.

**부수 확인**: 모든 측정에서 `r_min` = 진입 반경(150)이고 지평선 클램프(2.5M=25)는 한 번도
작동하지 않았다 → 초고 §V 한계 2를 "통상 사용에서는 작동하지 않는 안전장치"로 완화.

### §4.3 렌더링 성능 (`performance.mjs`)

```bash
node measurements/performance.mjs              # 기본: headed 3라운드
HEADLESS=1 node measurements/performance.mjs   # (권장하지 않음, 아래 참고)
SECONDS=5 ROUNDS=5 node measurements/performance.mjs
```

**⚠️ 반드시 headed로 돌릴 것.** 헤드리스 Chromium은 SwiftShader(소프트웨어 래스터라이저)로
떨어져 같은 구성이 **약 6fps**로 측정된다. 스크립트가 `WEBGL_debug_renderer_info`로 렌더러를
확인해 소프트웨어면 경고를 찍는다.

**환경**: GTX 1070, Chromium(WebGL 2.0/ANGLE D3D11), 1280×720, DPR 1, 격자 200×200, vsync 해제.
프레임 간격 3초 수집 → 3라운드 반복 → 라운드 평균의 중앙값.

| 질량 | 고무판 (ms) | Flamm (ms) |
|---|---|---|
| 0 | 0.282 (±0.013) | 0.290 (±0.038) |
| 1 | 0.597 (±0.058) | 0.615 (±0.023) |
| 2 | 0.601 (±0.026) | 0.620 (±0.010) |
| 3 | 0.615 (±0.047) | 0.619 (±0.053) |
| 4 | 0.635 (±0.063) | 0.635 (±0.038) |
| 5 | 0.617 (±0.028) | 0.615 (±0.020) |

- 60Hz 예산(16.7ms) 대비 **약 26배 여유**
- 0개 → 1개에서 프레임 시간이 두 배(변위 경로 활성화 **고정 비용**)
- **1~5개 사이는 분해 불가**: 변동폭 0.02~0.04ms < 라운드간 산포 0.06ms.
  → "개수에 따라 선형 증가"라고 **주장하지 말 것**
- 두 모델 간 차이도 산포 범위 내로 유의하지 않음

**왜 라운드를 반복하나**: 프레임 시간이 1ms 미만인데 `performance.now()`가 0.1ms로 양자화돼
있어(브라우저 보안 조치) 1회로는 미세 차이를 못 가른다. 열·스케줄링 드리프트도 순서 편향을 만든다.
